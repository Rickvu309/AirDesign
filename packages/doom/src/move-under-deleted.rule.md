# An edit never moves a layer under a frame it deleted earlier in the same edit, so the redo of its undo can land

`write` in `packages/doom/src/apply-edit.ts` refuses as `missing` a move whose frame, or a frame above it, the same edit deleted before it (`underLayerDeletedHere`). Such a move hides the layer inside the deleted frame, and after an undo, the redo, which puts moves first and deletes last, finds the moved layer's frame inside it and is refused `cycle` for good. Aira made it in one `airdesign_execute` call: a delete of G, then a move of F into J, which sits in G inside F (verdict 1510-559d9e2, finding 1). The rule is in the core, so a person, an agent and every later caller are refused alike. A move into a frame an earlier edit deleted still lands, as an offline tab may send one, and so does a delete after the move in the same edit. `packages/doom/src/apply-edit.test.ts`, `packages/doom/src/agent-edit.test.ts` and `packages/agent/src/edit-tool.test.ts` fail when such an edit lands, and the last also fails unless the answer names the change and says an earlier change deleted the frame.
