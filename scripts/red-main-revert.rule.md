# A red main is reverted to green by a machine, never for a race or an old fault: a certain red reverts the first red commit at once, a suspect red waits for a second red on the same test, and a test that fails at the last green commit too is recorded instead

`scripts/red-main-revert.mjs` and its verdict in `scripts/red-main-verdict.mjs`, run by `.github/workflows/red-main-revert.yml` each time `ci` completes on `main` or on a `red-main/revert-<sha>` branch, and tested on real red runs in `scripts/red-main-revert.test.mjs`, `scripts/red-main-verdict.test.mjs` and `scripts/red-main-green-rerun.test.mjs`. The green rerun is `scripts/green-rerun.mjs`.

- The first red commit is the first commit after the last push run that passed, or after the red run just before the first red the bot acts on, read in `main`'s first-parent order. A red run waits while a run before it still runs.
- A red is certain when a check step that is not a test step failed, such as typecheck, lint or the build, or a PowerPoint check other than the browser export spec. Those steps are deterministic and the last green run passed them at the parent, so the bot reverts at once and reruns nothing. A failed browser test whose own file the commits change is certain too.
- A failed unit or script test is certain only after its green rerun: the bot runs that one test again at the last green commit, the parent of the first red commit, in a worktree of its own, with the fast-check `seed` and `path` the red log printed. A test that passes there is the commits', and the bot reverts. A test that fails there with the same first error, numbers aside, is an old fault: no commit after the green one caused it. A rerun that cannot run or fails another way reverts nothing and says why on the `main is red` issue. A run with a certain check reruns nothing.
- A red the bot judges certain is reverted: it opens the revert and merges it once its `ci` passes while `main` is still red, since waiting would only keep `main` red longer.
- A red is a suspect when every failed test is an old fault or a browser or journeys test whose file the commits do not change, and at least one is the second kind, so the commits reach it only through app code. One red there may be a race, and a revert of a good commit costs its author a land. The bot opens the revert at once, since an open pull request costs nothing, but merges it only once a later push run on `main` fails the same test and that test then passes its green rerun: two independent reds on one test confirm it, and the rerun shows the green commit did not fail it. A single green pass cannot clear a race, so the second red stays the rule for browser tests; the rerun only stops a merge. When a later push run passes first, the bot closes the revert and records each suspect test that failed only once with `recordRace`.
- An old fault is recorded with `recordOldFault` as an issue titled `Old fault: <file> › <test>`, with the seed, the path and the command that replays them, and the bot reverts nothing for it. A later failure of the same test is rerun again, so a commit that does break it is still reverted.
- A failure is a race when an open `Race:` issue names every failed test. The bot comments on that issue and reverts nothing. The same test failing again in the next red run is rerun at the last green commit, and is certain when it passes there.
- A `Race:` issue is keyed by the test's file and title, never its line, so an edit above the test keeps one issue. An issue titled with a line still takes the comment.
- A run whose log names no failed test or step reverts nothing.
- The revert is a pull request opened as the owner with `RED_MAIN_TOKEN`, so `ci` and `bar` judge it like any other. Its body starts with the agent line, names the failed jobs and tests from `failureLines`, links the red run and the last green one, names the reverted pull request, and says whether it waits for a second red. When `bar` would call it lowering the bar, the bot countersigns it, because it puts back the bar `main` had before that commit.
- The bot merges a revert when its `ci` passes and the red is certain, from whichever comes last: the revert's `ci` or the push run that confirms the red. It closes the revert when a push run after the reverted commit passes. It never reruns `ci`, reverts a revert, or opens a second revert of one commit.
- Each verdict is a comment on the `main is red` issue through `scripts/red-main.sh`.

## Drill the live revert path

Run `gh workflow run red-main-revert.yml -f drill_sha=<full-sha>` and follow the dispatch with `gh run watch <run-id>`. Pick a small docs-only commit from the last 300 first-parent commits on `main` whose changes still apply in reverse.

The drill uses the same revert, push and PR creation code with `RED_MAIN_TOKEN`. The agent line and drill marker identify the PR. Each run gets its own `red-main/drill-<sha>-<run-id>-<attempt>` branch, outside the automatic merge trigger. The workflow waits for both `ci` and `bar` to start on the PR's head, then closes the PR and deletes the branch. If a check fails to start within five minutes, it still cleans up and reports failure.

Verify the PR author, the two workflow links, the closed PR and the deleted branch. The bot comments on the open `main is red` issue. If there is no open issue, it records the result in the workflow log and creates no issue.

## Drill the green rerun

Run `gh workflow run red-main-revert.yml --ref <branch> -f rerun_run=<red run id>` and follow it with `gh run watch <run-id>`. The `green-rerun-drill` job has no secret and only read permissions, so any branch can dispatch it. It reruns each failed test of that run at the run's parent, prints `fails`, `passes`, `unclear` or `unrun` for each, and prints the seconds the setup and the reruns took. It reverts, records and comments nothing. Drill run 44775404486 on run 44764886281 measured what a rerun adds to the bot on GitHub: 18 s to set up pnpm, Node with the pnpm store and Postgres, 3.7 s for the worktree and offline install, 1.1 s for the property rerun, and 27 s more for a browser rerun (5.5 s for the browser, 21.7 s to build and run the test).

## Seeds per commit

Vitest gives every fast-check assert a seed made from the commit, the test's file and name and which assert of the test it is, in `scripts/property-seed.mjs`. One commit draws the same inputs on every run, and the next commit draws new ones, so the inputs explored across commits stay as wide as a random seed. A seed or path a test passes to `fc.assert` wins. The failure prints the seed and path; `AIRDESIGN_PROPERTY_REPLAY='{"seed":<seed>,"path":"<path>"}'` replays them.
