# `pnpm land` judges a head only by the checks GitHub requires for `main`, so a check that is not required never holds a merge or counts as the pull request's failure

The required set is read from GitHub in the one pull request query: a check run whose `isRequired(pullRequestNumber:)` is true, plus the contexts `refUpdateRule` lists for `main`, so a required check that has not started yet is waited for and never skipped. Land merges when every required check passed and none failed or runs, and it fails the pull request the moment a required check fails, without waiting for the rest of the run. Any other check, `mutation` and CodeQL among them, is named in land's state line as `not required, blocks nothing: mutation still running` and decides nothing. When GitHub names no required check, land merges nothing on that. A failed required check that a newer run of its workflow replaces counts as running, so a fresh run on the same head is not read as the old failure, and the old run's `mutation` still going is not read as the fresh run starting. A merged pull request leaves `mutation` to finish and report on its head: no job of `ci` needs it, nothing cancels a pull request's run but a newer run of that pull request, and the push run on `main` and the red-main bot never wait for it (`scripts/merge-queue.mjs`, `scripts/land-follow.mjs`, `scripts/fresh-run.mjs`, `scripts/land-status.mjs`, `scripts/land-required-checks.test.mjs` replays pull request 1049 with `ci` and `bar` passed, `mutation` running and CodeQL pending)
