# Land takes one fresh run for a test failure the pull request did not edit, and records a race only after that run passes the test

Evidence decides, not the change map. A pull request that changes the failed test file, or any browser or journeys test or its setup, owns the failure and takes no fresh run. A `design-states` failure is one state, read from the `"page"` field: it is owned only when the diff changes that state's file, `.agents/skills/verify-airdesign/look/states.mjs`, or the spec itself. Another browser spec, or `tests/browser/spec-seconds.json`, leaves it outside the diff. The race is titled `Race: design-states › <state>`, and a hand-filed title with a journey suffix is the same issue. Missing job logs, unread files and a failed step that is not a browser or journeys step stop too. Every other named browser, design or journeys failure takes one fresh run per head, even when the change map says the diff can affect the failed job: the map works at job scope, and nearly every app change reaches every browser job.

Land comments on the pull request that the failure is in tests it does not edit and that one fresh run will tell. It closes and reopens the pull request, or queues it again after a queue drop. The comment marks the head and the failed run. A reopen selects every ci part so the failed jobs run again. Land files a `Race:` issue only when the fresh run on the same head passes ci and executes the failed jobs successfully, so a test that fails and then passes on one head is the evidence. It names each recorded issue in its output. When the fresh run fails the same test again, land records nothing, says the test failed twice on this head so the change most likely causes it, and stops for a fix. A merge-queue run on a different commit cannot confirm a race on the pull request head. `ci` fails attempts after the first.

The red-main bot keeps the change-map verdict for a failure on `main`, through `byMap` (`scripts/red-main-revert.rule.md`).
