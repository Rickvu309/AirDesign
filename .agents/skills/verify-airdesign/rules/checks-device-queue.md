## device-queue

A person sets a line's width twice in the design panel, then clicks Undo, then Redo, while the server has not answered. A panel change paints at once, painted ahead: it plans against the deck the canvas shows, with the edits the device has not written yet on top (`paintingAhead` in `apps/web/src/editor/painted-ahead.ts`). Its link on the editor's chain then does only the device's work: it plans against the deck on the device, writes a pending row, records the step and paints the device's deck. A link the device refuses also paints the device's deck, so a width painted ahead on an element the device reads as gone goes at once. The send starts after the link and settles on its own. The device sends its pending rows one batch at a time, seals a batch with a once before its first send, and confirms the rows when the answer comes. An answer may come late or be lost, and an agent may delete the element on the server, which then refuses the person's rows. A width is a digit (1 the file's, 2 and 3 the person's, 0 gone), and the rows, the server's rows and the undo and redo lists are numbers whose digits are their entries, because the graph reader takes only plain values.

- `PaintsBeforeAnswers`: whatever the server does, never answering included, the person clicks through both widths, Undo and Redo, and each click paints. Fairness is on the clicks alone. Harm if broken: the second Redo paints only once the first one's answer comes back, and a reload before then loses it, the line-style fault `2abaf256` fixed.
- `ShownIsDevice`: the canvas shows the deck on the device, rows still pending included, but for the moment between a set-aside and its repaint.
- `SettledShowsServer`: once every answer came, the canvas shows the server's deck, apart from an agent's delete the device has not read yet; it reads it when it next follows the deck, which lost-answer models.
- `LandsInOrderOnce`, `NoEditLost`: the server applies the person's rows in the order the device wrote them, each once, and a row leaves the device only once the server applied it or refused it because the element is gone. Harm: a width applied twice, or a Redo that never reaches the server.
- `UndoTakesLastStep`: while the element is there, the top undo step is the one that brought the device to what it shows, and the top redo step starts there. Harm: Undo turns back an older width, or a step the server has not answered.
- `ToldOnlyWhenGone`: Undo or Redo changes nothing only when the device reads the element as gone, so the person's own rows, answered or not, never make a turn fail, and a Redo straight after an unanswered Undo lands.
- `NothingAfterGone`: once the device read that the agent deleted the element, it writes no row for it, so no Undo or Redo brings it back.

Bounds: one element, one line width, the clicks in the order first width, second width, Undo, Redo, one lost answer, one agent delete. 412 states, 802 edges. Run: `pnpm check:specs device-queue`. Replay: `apps/web/src/device-queue.test.tsx` renders the real `useUndoList` and `useUndoTurn` in jsdom, clicks through the real `changeDesign` and the Undo and Redo buttons, over the real device queue (`connect` from `packages/live`) on the fake IndexedDB of `packages/live/src/browser-fixtures.ts`, with `memoryRemote` as the server behind a `fetch` that holds each commit until the model's `Apply`, `Refuse`, `Answer`, `Lose` or `SetAside`. It takes all 802 edges in 241 walks. A click edge waits for its link to finish, so a link that waits for the server fails the edge. The replay holds each `flush` call until the model's `Send` and runs one flush for all the calls it held, since calls that wait to start send the same rows; after a lost answer it calls `flushPending` itself, as `resendPending` does. After every step it compares the pending rows and how many carry a once, the request on its way, the server's rows on the element, whether the element is gone, the deck on the device, the rows set aside, what the canvas shows, the undo and redo lists and whether the person was told, and it checks that rows waiting on the device always have a send asked for. The canvas is a stand-in that keeps the register `showRegister` was given, the way the editor paints a trait row when the deck's structure changes; `Reconcile` restates `reconcile` in `useDeckOpen`, which is not exported. Code: `changeDesign` and `changingDeck` in `apps/web/src/design/design-change.ts`, `applyChange`, `planned`, `stored` and `landedBefore` in `apps/web/src/design/trait-edit.ts`, `turnAfter` in `useUndoList` and `turn` in `useUndoTurn` (`apps/web/src/editor/use-undo.ts`), `turnBack`, `sent`, `sentCommand` and `recorded` in `apps/web/src/undo-list.ts`, `undoOf` and `redoOf`, `flushPending` in `apps/web/src/commit-edit.ts`, `sendRows`, `sendBatches` and `asideRefused` in `connect` (`packages/live/src/cache.ts`), `sealRows`, `confirmRows`, `setAside` and `takeAside` in `packages/live/src/held.ts`, `refusedRows` and `withSlides` in `packages/live/src/slide-replay.ts`, the set-aside repaint in `useDeckOpen`, and the server's once in `commitEdits` (`apps/api/src/saved.ts`), which the replay's `memoryRemote` keeps the same way.

Leaves out: a click and its link are one step, so a state never holds a width painted ahead of its link; `device-queue.test.tsx` holds the chain and checks that a panel change paints while the device still has the old width, and `tests/browser/paint-before-save.spec.ts` sets a font size while the device's store is held. Also, so an answer or a set-aside that lands in the middle of a link's device work is not modelled; a lost request before the server and a lost refusal, each of which leaves the sealed batch pending to go again, as a lost answer does; the page's reload and an old page's request, the device following the deck and adopting an agent's write, which lost-answer models; Undo or Redo in another order, a panel change after Undo, a second lost answer and a number field's session, which joins its records into one step (`joined`, typing). The design panel's own reads of the deck and the canvas's paint of a line are outside it. A box move is a link on the same chain (`onBoxes` in `editableSlide`), and its boxes are painted ahead until it stored them: it writes and records on the device, a move into or out of a frame included (`commitPlace` in `apps/web/src/editor/group-actions.ts`), and its send starts after the link. The model has no move; `apps/web/src/editor/box-move-turn.test.tsx` checks that the next link runs while the server holds a frame move's answer, and that an Undo straight after a nudge undoes the nudge. A link that fails hands its failure to its caller and the next link still runs (`turnAfter`, `apps/web/src/editor/use-undo.test.tsx`).

## painted-edits

This model separates what the canvas shows from what the device has stored. An export snapshots the edits painted when it starts and reads the device after their holds release. A new layer can paint before its insert reaches the device. Typing or dragging the layer can also paint during that gap.

- `ExportIncludesPaintedEdits`: the export contains each edit that painted before the export request. The panel and drag take their record holds before they paint. The export waits on the holds that exist at the request.
- `LayerEditFollowsInsert`: the device stores the insert before storing typing or a move on the new layer. Typing waits for the earlier insert lane. A move waits for the earlier record holds before it reads and writes the layer.
- `ExportFinishes`: when local writes finish, the export can finish. A design change or undo snapshots the prior holds so it cannot wait on its own hold or a later turn.

Bounds: one panel edit or one insert and one edit on the new layer, one export, successful local writes, no network. The flags 1 and 2 represent the first and later edit. Run `pnpm check:specs painted-edits`. The controlled-gap tests in `apps/web/src/design/design-change.test.ts` and `apps/web/src/editor/editable-slide.test.tsx` drive the app code through the interleavings that fail when the waits are missing. The device-queue replay above still covers the network and undo after local storage. The model leaves out storage refusals and the file writer itself.
