# Checks on how the editor follows the network

Same fields as [checks-document.md](checks-document.md). connection is replayed in `apps/web/src/connection.test.tsx`, which renders the editor's network hook and its status in jsdom: `pnpm vitest run apps/web/src/connection.test.tsx`. The order and once of the rows a send carries is offline and device-queue, a lost answer is lost-answer, and two tabs on one deck is tabs. This check holds none of them: the device's queue is one flag, rows wait or none.

## connection

The open editor keeps three flags in `useDeckStatus`: online, the browser's `navigator.onLine`; offline, whether the last send found no server; and pending, whether rows wait on the device. Pending has one owner: `watchUnsent` in `packages/live/src/held.ts` tells the editor after every committed write and every read of the deck's rows, so pending is the model's `rows` and no send's answer writes it. `saveStatus` turns them into the line beside the deck name: Saved, Saving…, Offline, saved on this device, or Unable to reach AirDesign. `useNetwork` sets offline on the browser's offline event, sends on its online event, and runs `resendPending` while online, offline and pending all hold. An edit writes a row, which sets pending, and sends. Every send is `flushPending`, and `settle` reads its outcome into offline: offline sets it, sent and kept clear it, and empty leaves it as it was. A send that found no rows when its turn in the lane came marks its answer `empty` (`sendRows` in `packages/live/src/cache.ts`), and when rows wait after it `flushPending` answers empty: it carried nothing, so it says nothing about the server. `resendPending` rests and sends again on offline or empty, and ends on any other outcome. Sends to one deck wait in one flush lane, so only the first is on the wire. The row commit and a follow's refresh share a second lane, `serial` in `packages/live/src/deck-lane.ts`. The opening index page stays in the flush lane and off that second lane, so a follow can read the deck while the page is on the wire. The send carries every row the device holds when it starts. When it carries no rows it asks no server. After a successful or empty send, `flushPending` reads sent if no rows remain on the device, and if any do, kept when the send carried rows and empty when it carried none.

- `TellsWhenOffline`: the browser going offline reads Offline at once, with or without rows waiting. Review finding F6 asked for this; `f8ac97e5` gave it, and `tests/browser/save-status.spec.ts` drives it with the browser context offline. Harm if broken: a person who lost the connection learns it only when an edit fails.
- `SavedOnlyWhenLanded` requires an empty device queue whenever the open editor reports Saved. The model exercises a second edit while an earlier commit is on the wire, and a deck that opens with rows from an earlier visit while its opening send is in the lane. `tests/browser/save-status.spec.ts` holds the second commit of a text or slide edit while the first lands, and reopens a deck with an unsent edit while its commit is held. Before `watchUnsent`, pending was a flag every send's answer wrote, and the reopened deck read Saved until the opening send answered: TLC fails the old model in its initial state.
- `OneNoticePerOutage`: while rows wait in the open editor, only their landing clears offline, so the offline notice, or Unable to reach AirDesign once the browser is back, stays one notice until the rows land. It failed in 5 steps once the deck's opening send was modelled with nothing waiting: the browser goes offline, the opening send leaves carrying nothing, the person edits, and the opening send answered kept, so `settle` cleared offline. The notice left, and the edit's own send failed offline and showed it again as a second toast. That is the strict-mode failure of `the offline notice slides in and leaves by the top edge` in `tests/browser/notice-motion.spec.ts` that dropped merge-queue runs. Harm if broken: one outage shows the notice, takes it away while nothing is saved, and shows it again.
- `NoUnreachedWhenAnswered`: online, with nothing waiting, every send answered and no resend due, the line never says AirDesign was not reached.
- `StopsOnLeave`, `OneLoop`: once the editor closed no resend loop runs and none of its sends is read, and at most one loop's send is in the lane. The cleanup of `useNetwork`'s effect aborts the loop; `resendPending` checks the signal after its pause and after its send, so a stopped loop sends nothing more and settles nothing. A send it had already asked for stays in the lane and goes; it carries rows the person wrote, so that is harmless.
- One send at a time: an online event while a send or a resend is running does not put the same rows on the wire twice at once. `serial` in `packages/live/src/cache.ts` holds every send to one deck in a lane, so the later send starts only after the earlier one answered and carries what is still waiting, or nothing. The model has the lane by construction; device-queue's replay drives `serial` itself.

- `SavedWhenSettled`: online, with nothing waiting, every send answered and no resend due, the line reads Saved.
- `SavesOnceAnswered`: once the browser stays online and AirDesign answers, the rows go and the line reads Saved.

Both failed before `flushPending` asked the device whether rows still wait, in 13 steps: AirDesign stops answering, the person edits, the send answers offline and the resend loop starts; AirDesign answers again, the loop's pause ends and it asks to send; the browser goes offline, which stops the loop with its send still in the lane, and comes back online, which adds the online event's send and starts a new loop. The stopped loop's send carried the rows and landed, but nobody read its answer. The online event's send carried nothing and answered kept, so `settle` cleared offline and left pending, the effect stopped the new loop, and the line read Saving… with nothing left to send, until the person's next edit. The empty send now checks the device queue and reports sent when it is empty. `apps/web/src/connection.test.tsx` walks that run through the real hook and reads Saved. `tests/browser/save-status.spec.ts` holds a resend on the wire, dispatches offline then online, lets the send land, checks that the server revision rose once and reads Saved without another edit. The `editor-reconnected` look state drives the same sequence on main and this change.

Bounds: the deck opens online with its opening send in the lane, with nothing waiting or with one row from an earlier visit, which counts as the one edit. An edit before the opening send leaves is that second start, so the first edit comes after the opening send left; two network changes (offline, then online), one outage of AirDesign, and the person leaves only while a resend loop runs. A second edit can overlap the first send on the uninterrupted online path. 406 states. Run: `pnpm check:specs connection`. Replay: `apps/web/src/connection.test.tsx` renders the real `useDeckStatus` and `useNetwork` in jsdom and takes every edge of the graph. The browser's events are real `offline` and `online` events with `navigator.onLine` set to match. An edit is a device write, which tells `watchUnsent`'s watcher, then `commitKept` and `settle`, as `commitEdit` does in `editableSlide`. `watchUnsent` is a stand-in that tells the hook what the model's `rows` says after each device write and each `Answer`. Each walk opens the editor at its start, with the device holding a row when the start says so, and sends the opening `flushPending` as `useDeckOpen` does; `packages/live/src/unsent.test.ts` drives the real `watchUnsent` on IndexedDB for a reopened deck. The lane is a stand-in for `connect(...).flush`: each call joins it tagged with the step that made it, a resend's call with the signal of its loop's pause, and `Answer` resolves the first with `{ ok: true }` when it carried rows and AirDesign answered, the empty queue's `{ ok: false, refusal: "batch", empty: true }` when it carried none, or rejects it with a `TypeError`; the link's `pending` then lists a row when the model says rows wait. `pause` is held until `Retry`. After every step it compares the three flags, with a closed editor's pending read as false since nothing shows it, the save status, the lane with a stopped loop's send told apart by its aborted signal, and whether a loop rests or waits on its send.

Leaves out: a send failing with the browser online but its request lost after the server applied it (lost-answer); `flushOriginal` after a send, which the online event's handler still runs after the editor closed and which sends only the device's held original and pictures; refusals from the server (signed out, storage, size, set aside); the time between a state change and React running the effect, which the model and the replay take as one step; and an edit painted ahead of its row. `useLeaveGuard` in `apps/web/src/editor/leave-guard.ts` counts that edit as pending for the status and for the browser's prompt before the tab reloads or closes, so the model's rows stand for both; `apps/web/src/editor/leave-guard.test.tsx` and `tests/browser/leave-before-stored.spec.ts` hold it.
