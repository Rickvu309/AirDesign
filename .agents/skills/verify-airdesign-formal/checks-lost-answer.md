# Checks on a lost answer to a person's command

Same fields as [checks-document.md](checks-document.md). The replay drives the device queue on IndexedDB: `pnpm vitest run packages/live/src/lost-answer-replay.test.ts`.

## lost-answer

One slide command a person queued on one device, while answers are lost and the page reloads: the device's pending row, its mirror of the server's deck, the once the row is sealed with, the server's answer to a once it already spent, and when the page sends the row again. The offline model is silent here: it has no mirror, no adopt and no lost fetch, and its `Crash` ends the run.

- `LandsOnce`: the command lands once however often it is sent. Harm if broken: a slide added twice.
- `OneRow`: the mirror holds the command at most once, and once the pending row is gone it holds exactly what the server holds. Harm if broken: a reload after a lost answer leaves the device with the command twice, and every later edit is decided on a deck the server does not hold.
- `OpenNeverFails`: the deck opens whatever the mirror and the pending rows hold, because `withSlides` skips a copy it cannot apply. Harm if broken: `person edit refused` on the next open and an empty editor on every open after it, with the server's copy whole. Today's code failed both properties: TLC finds `OpenNeverFails` broken after Send, Land, Lose, Adopt, and `OneRow` broken when the next answer adds a second copy.
- `ResentOnceReached`: a pending row eventually lands or receives a terminal refusal. A lost request or answer leaves a flush due, so the edit can land when the server answers again.
- `RefusedStaysPending` and `RefusalLastsUntilReload`: a terminal refusal leaves the row on the device and blocks sending that deck until reload. The replay checks that a queued flush returns the same refusal and issues zero requests. The old code failed after Send, Refuse, FlushAfterRefusal because the second flush sent the sealed row again.

Bounds: one command, two reloads, one request of a closed page still on its way, one write by another writer. TLC checks 279 states. `Lose` stands for every fetch that throws: the browser offline, the server not reached with the browser online, and every answer `post` in `packages/live/src/remote.ts` reads as a throw, which is any 5xx and a 2xx whose body is cut off. `Refuse` uses a storage answer. The page stores it in `keepCommitRefusal`. A size refusal for a batch within the device's limit follows the same path. `mine` says the live page wrote the pending row itself (`pageEdits` in `packages/live/src/device.ts`, read by `takeEdits`); a reload forgets it, so an answer to a row an earlier page wrote leaves the mirror's revision where it was, and the next follow reads the deck. The copy stores the revision it holds and `confirmRows` adds nothing when it holds the answer's revision or a newer one; with one page that revision equals `known` whenever an answer comes. Run: `pnpm check:specs lost-answer`. Replay: `packages/live/src/lost-answer-replay.test.ts` drives every edge through `connect`'s `flush`, `open`, `openDeck` and `follow` on IndexedDB, with `memoryRemote` answering a spent once as `commitEdits` does, and opens the device copy in every state. The send goes through `httpRemote` and `post` on a held fetch: `Lose` ends a request with a thrown fetch, a 502 page or a 500, and an answer with a 200 cut off or a 504, and the flush must throw a `TypeError`, which `flushPending` in `apps/web/src/commit-edit.ts` reads as `offline`, so a resend is due; `Answer` must flush ok. It does not compare `due` itself: the resend is `resendPending` in `apps/web/src/deck-resend.ts`, which `useNetwork` runs while the last flush threw, the browser is online and an edit is pending, and which `apps/web/src/deck-resend.test.ts` and the real-save browser spec `an edit made while the server cannot be reached lands once it answers again, with no new edit` cover. Code: `sendBatches`, `asideRefused` and `adopt` in `packages/live/src/cache.ts`, `withSlides`, `landed` and `refusedRows` in `slide-replay.ts`, `sealRows`, `confirmRows`, `takeEdits`, `setAside` and `takeAside` in `held.ts`, `commitEdits` in `apps/api/src/saved.ts`. Leaves out: rows the server's copy refuses for another reason, such as a slide id another writer took or text on a slide another writer removed. `sendRows` sets those aside after reading the server's copy again, and `flush` returns their count once, so the editor says `Unable to save some edits`; `packages/live/src/lost-answer.test.ts` covers that, and the text, notes, table, box, picture and slide-move shapes of a lost answer. The model omits the recovery of old batches that exceed the device's current size limit. `sendBatches` cuts every batch it builds to fit `limits.body` (`nextBatch` in `packages/live/src/commit-body.ts`), and `valueChange` and `slideChange` refuse a row no request can carry. When the server answers `size` to a sealed batch the device measured over the limit, which only a build before that cut sealed, `sendBatches` unseals it and sends it again in batches that fit, or sets a single row aside; `packages/live/src/cache-size.test.ts` and the `large-edits` browser spec cover it. Two tabs of one browser that send the same sealed row at once are not modelled: an answer the second tab reads after the first adopted is dropped like any revision the copy holds, and a second copy in the mirror is skipped by the view and replaced by the next adopt. Two tabs with one request on its way at a time are [tabs](checks-tabs.md).
