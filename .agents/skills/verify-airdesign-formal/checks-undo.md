# Checks on a person's own Undo and Redo

Same fields as [checks-document.md](checks-document.md). person-undo is replayed in `tests/spec-replay.test.ts`; typing in `apps/web/src/typing.test.tsx`, which renders the editor's undo parts in jsdom: `pnpm vitest run apps/web/src/typing.test.tsx`. The undo of an added or removed element is element in [checks-document.md](checks-document.md), and a run's own Undo is undo there and slide-undo in [checks-slides.md](checks-slides.md).

## person-undo

A person's Undo and Redo of their own text edit, beside an agent run.

- `UndoShowsBefore`: an undo or redo shows exactly the text it went back to.
- `NeverCoversAgent`, `AgentRowStays`: a person's undo never lands over an agent row that shows, and only the run's own Undo hides that row. Harm: a person's Ctrl+Z erases Aira's work.
- `DroppedIsTold`: an undo that changed nothing is always told.

Bounds: up to four person rows, one agent row. Run: `pnpm check:specs person-undo`. Replay: `tests/person-undo-replay.ts` through `undoOf`, `redoOf` and `decide`. Code: `undoOf`, `redoOf` in `packages/document/src/person-undo.ts`, the stack in `apps/web/src/undo-list.ts`. Leaves out: box undo, slide undo (`slideUndoable`) and notes edits, which take the same path as text. The undo of an added or removed element, with another tab and an agent's run in between, is covered by element. An undo while typed edits are still being recorded or sent, and the browser's own undo, are typing.

Sync: `8eef931306bc47b21b66b33dc5d7dc14634b9f4f`.

## typing

A person types two letters of speaker notes, then two over a text box, and presses Ctrl+Z, later Ctrl+Shift+Z, while what they typed is still on its way. Each edit is written to the device at once. A keystroke's undo record lands once the device answers and the session's text before is read (`editText` in `apps/web/src/editor/editable-slide.tsx`); a notes edit's lands once the notes edit before it reached the server (`useNotes` in `apps/web/src/notes-edit.ts`). Each edit then goes to the server, and the box stays busy until its keystrokes got there. A text is a number: 0 the text before the typing session, 1 its first letter, 2 the whole new text. The undo list is a number whose digits are its entries (1 and 2 the notes, 3 and 4 the box), because the graph reader takes only plain values.

- `UndoRestoresBefore`: one undo after typing holds and shows, in the element it turned, the text from before the typing session, never a part of the new text. Harm if broken: Ctrl+Z straight after typing "New" over "Old" shows "N", PR 427's fault.
- `NeverPartOfNew`: once the whole new text is typed, the box never shows only its first letter.
- `NoUndoOnMissing`: an undo or redo never reads a list that is missing a record already typed. The ghost `missing` is set when the undo reads the list (`Turn`).
- `TurnLands`: every undo and redo asked for after typing lands. Harm if broken: Ctrl+Z straight after typing does nothing, or says nothing changed.
- `ShownIsDeck`: after an undo or redo, the box and the notes show what the deck holds. Harm if broken: the box keeps the typed text while the deck went back.
- `RedoRestoresTyped`: a redo brings back the whole typed text.
- `UndoTakesLastTyped`, a known failure in `Typing.known.cfg`: the element one undo turns is the one the person typed in last.

Bounds: one box with two keystrokes, one slide's notes with two edits typed before the box, one undo, then one redo, no typing after the first Ctrl+Z. 266 states, 607 edges. Run: `pnpm check:specs typing`. Replay: `apps/web/src/typing.test.tsx` renders the real `Passage`, `useUndoList`, `useUndoTurn` (with its `useUndoKeys`) and `useNotes` in jsdom over a real paint store and the parts of `scripts/pptx-fixtures/clean.pptx`, and takes all 607 edges in 211 walks from the start. So the undo's own waits, `turnBack`, `showTurned`, the repaint as the person and `notesShown` are the product's, through `recordsInFlight`, `recorded`, `liveRepaint`, `busyElements`, `showText`, `commitEdit`, and `decide`, `undoOf` and `redoOf` on a register. The device (`connect`) is a stand-in: a write lands on the register at once, its answer waits for the model's `RecordNotes` or `RecordText`, its upload for `UploadNotes` or `UploadText`, and the undo's deck read for `Turn`. After every step the test compares every model variable with the code (the box's text in the DOM, the notes shown, the deck, the undo and redo lists, the counts), checks the box is busy exactly while a keystroke is unsent, and checks the undo reaches its deck read exactly when the model's waits are met. `KeyUndo` and `KeyRedo` press the keys on the box, or on the page when only notes were typed, and check the browser never gets them; `MenuUndo` sends `historyUndo` and checks the box refuses it. Code: `recordsInFlight`, `recorded`, `turnBack` in `apps/web/src/undo-list.ts`, `liveRepaint` and `busyElements` in `apps/web/src/live-repaint.ts`, `useNotes` in `apps/web/src/notes-edit.ts`, `undoKey` and `useUndoKeys` in `apps/web/src/editor/undo-keys.ts`, the `beforeinput` refusal in `packages/render/src/passage.tsx`, `turn` and `showTurned` in `useUndoTurn` in `apps/web/src/editor/use-undo.ts`, and `editText` in `apps/web/src/editor/editable-slide.tsx`.

Leaves out: the replay restates `editText` instead of driving it, since `editableSlide` needs a painted deck: it holds the box and the records, reads the text before at the session's start and records in the paint step. `tests/browser/person-undo.spec.ts` drives it in a browser. The model takes the text before as read from the device before the first keystroke's write lands; both are IndexedDB requests in `packages/live`, and nothing here checks their order. It takes the device as answering writes in typing order, and a notes edit whose queue is free as recording in the task its answer comes in, so a keystroke records ahead of an earlier notes edit only while that edit waits for an upload (`RecordText`). Uploads finish in any order in the model; the device sends them one at a time in call order (`serial` in `packages/live/src/cache.ts`). Also left out: typing after Ctrl+Z, notes typed after the box, a second undo, Ctrl+Z inside the notes field (a form field, so the browser's own undo of the field), boxes, slides and added elements, the server's answers that repaint (`reconcile`), and agent runs (person-undo).

Known bug, from `3b0c63e1`: a notes edit records its undo entry inside the notes queue, after the notes edit before it reached the server, while a keystroke records as soon as the device answers. A person who types two letters of notes, clicks into a box and types over its text while the first notes letter is still sending gets the list notes, text, notes, and Ctrl+Z puts the old notes back and leaves the typed text. Harm: on a slow network the first Ctrl+Z after typing over a text undoes the speaker notes instead. TLC's trace in `Typing.known.cfg`: TypeNotes, TypeNotes, TypeText, RecordNotes, RecordText, UploadNotes, RecordNotes, UploadNotes, KeyUndo, Turn. The `it.fails` test in `apps/web/src/typing.test.tsx` replays it on the code. Read from the code, not replayed: a second Ctrl+Z brings the text back, and a third finds the notes no longer show the first notes entry's text and says nothing changed.

Planted faults. Each old behaviour PR 427 fixed, and the notes wait PR 418 added, put back in the model and then in the code:

Without `NoUndoOnMissing` and `TurnLands`, the model with either wait removed passes the other properties (376 and 408 states): a missing record makes Ctrl+Z do nothing or say nothing changed, never land a wrong text, because `undoOf` lands only while the deck shows the entry's text.
