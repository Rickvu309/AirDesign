# Checks on a run's slide calls, their Stop and their Undo

Same fields as [checks-document.md](checks-document.md). The replays start the real API on their own Postgres database: `pnpm vitest run apps/api/src/slide-run.test.ts apps/api/src/slide-sibling.test.ts apps/api/src/slide-undo.test.ts`.

## slide-run

An agent run r that added a slide, an agent call (add_slide or read_deck) and the agent's stop_run of r as two MCP requests whose steps interleave. Each request is admitted once, then `settledCall` in `packages/mcp/src/server.ts` runs up to `commitTries` (three) tries. Each try loads the turn row (`turns.load`), reads the deck (`readSaved`) and decides (`callTool`), and `commitEdit` writes the deck only if `deck.saved` still has the revision that try read (`writeRevision`). A write lost to another one goes back to load the turn and read the deck again. After the tries the request saves the turn row once (`settleTurn`, `storedTurns` upsert), and `createServer` answers only after that save (`turnSaved`), so the answer is the request's last step. `element` says whether r also holds an element, and `ended` whether the deck records r ended. stop_run of r writes that record (`endSlides` in `packages/engine/src/call.ts`), so a stop always changes the deck. `runFenced` treats r as over once the deck records it ended or r holds an element and has none running: `liveTurn` then does not take r as the turn's run, so a slide call adds under the caller's own run, and `agentSlide`'s `runFence` refuses r `run-fenced`.

- `SlideOnRead`: a slide of r lands only on the revision the agent read, or on revisions only r wrote after it. It said "only on the revision the agent read" until the slide-sibling change, which made the run's own writes leave its base fresh. Harm if broken: an agent adds a slide to a deck it did not see.
- `TurnCallsLand`: a slide call of the turn's live run, on a deck only that run wrote after the agent's base, is not refused for its base. The old rule, `base = rev`, breaks it: the agent's second slide call, sent with the base it read before its first, was refused stale.
- `WritesOnRead`: every write lands on the revision its own try read, so a retried call is judged on the deck as it is after the write it lost to. Harm if broken: a retry writes over the edit it lost to.
- `AppliesOnce`: a call changes the deck at most once, however many tries it took. The loop ends on a landed write. Since the slide-sibling change, that is the only guard: a re-run of the same add_slide on the deck its own write moved finds its base fresh, so it would land a second slide. A client that re-sends an add_slide whose answer it lost lands it once when both sends carry the same once (`app.airdesign/once` in the request's `_meta`); slide-sibling checks that as `SentTwiceLandsOnce`. A re-send with no once still adds a second slide.
- `CountsOnce`: a call counts as one tool call, however many tries it took. The replay checks it against the `tool` events in `session.caller_log`.
- `TurnNeverOlder`: a saved turn row never replaces one with a newer revision.
- `StopFences`: no slide of r lands once its Stop took effect. Harm if broken: after Stop answered, the agent's slide still lands.
- `StopFencesHeldRun`: the same for a run that holds an element. `StopFences` implies it; it stays as the check `19e91f75` added.
- `NoTurnWhileRunning`: a turn row that names no run is saved only after r's element stopped. So `slideTool`'s two branches for a live run with no live turn, joining it through `heldRun` and stopping it on a fresh base, are never taken here; the idle window, which this model leaves out, is how a real call reaches it.
- `TurnStaysEnded`: after stop_run of r answered ok, the turn row no longer names r. Harm if broken: the stopped run is live again, so the agent's next calls join it.

`last` is the deck's `lastRun` (`landed` in `packages/engine/src/call.ts`): the run whose edit or slide calls wrote its latest revisions, from the revision they began on. A write that records no run, such as the stop, leaves `lastRun` naming an older revision, so it no longer counts. A person commit that holds only sizes the open tab measured from the text (`measuredOnly`, `measuredFrom` in `call.ts`) carries `lastRun` to its revision, so the run that changed the text stays fresh. `readFresh` in `agentSlide` takes a base that is the deck's revision, or one that `lastRun` of the caller's run reaches back to. `covers` says whether it reaches the agent's base, and the ghost `foreign` whether a write other than r's landed after that base.

What the retry changes here: an add_slide that loses its write to the stop tries again, reads the stopped deck, and is refused stale, because its `base` no longer matches and the stop wrote no `lastRun`. A stop_run that loses its write to the agent's slide tries again on the fresh turn and deck and lands; before PR 391 it was refused stale. Neither fixes or opens a bug.

Bounds: one run r, one stop request, at most two agent calls, the second one an add_slide, one element, `Tries = 3`. 460 states. With the second call free to be a read, the model passes 500 states once the second add_slide can land; read then read and add_slide then read left with it. A first-call read still races the stop's turn save. Under these bounds the agent loses at most once and the stop at most twice, so the third-try refusal is not reached; `packages/mcp/src/server-commit.test.ts` covers it. Run: `pnpm check:specs slide-run`. Replay: `apps/api/src/slide-run.test.ts` drives every edge through the real `serveMcp`, on the test's own Postgres. `mcpSteps` in `apps/api/src/mcp-steps.ts` serves each request with its own pools that pause before each turn load, deck read, deck write and turn save, so a model step is one statement; the deck read inside `commitEdit` after a lost write is not a step. The replay sees a request end when `serveMcp` returns, so it cannot tell an answer sent before the turn save from one sent after; `packages/mcp/src/server-commit.test.ts` checks that order. The request's pause point is its pc, so the replay checks where the code is, not only what it wrote. The test also checks that the graph holds a retried agent call and a retried stop. Code: `settledCall` and `createServer` in `packages/mcp/src/server.ts`, `editDeck` and `addTurn` in `packages/mcp/src/edit-tool.ts`, `agentSlide`, `runFence` and `runFenced` in `packages/engine/src/agent-slides.ts`, `stopRun` in `packages/mcp/src/call-tool.ts`, `endOnTouched` and `endSlides` in `packages/engine/src/call.ts`, `settleTurn`, `liveTurn` and `heldRun` in `packages/mcp/src/turn.ts`, `storedTurns` in `apps/api/src/agent-turn.ts`, `serveMcp` and `commitEdit` in `apps/api/src/mcp.ts`. Leaves out: the idle window (turns stay live), the limits beyond counting a call once, the `indexing` refusal and its refund (the deck is fully indexed), the other three slide tools (they share `agentSlide`), edit_deck's `add`, `set`, group and diagram changes (each checks `readFresh`, the add, group and diagram through `ready` in `packages/engine/src/agent-elements.ts` with `runFence`, and `landed` records their run), and Aira's own loop. The replay sends no once, so `prepare`'s read of `deck.once` never answers here; slide-sibling has it. `mcpSteps` finds its pause points by the SQL text in `saved.ts` and `agent-turn.ts`; if that text changes, change `gateOf` there.

Fixed bugs. From `30244817`: stop_run of a run that only added slides answered ok and changed nothing in the deck, so an add_slide that read the turn and the deck before the stop landed under the stopped run. The stop now writes r ended, so that add loses its write, retries on the new revision and is refused stale, and a later call starts a new run. `apps/api/src/slide-run-stop.test.ts` replays it. From `50489172`: the turn upsert replaces a row of the same revision, so an add's turn save at the stop's revision wrote r back. Two writes never share a revision, and a stop of r that changes nothing finds r already ended, so no slide of r can have landed at its revision: the save of a raced add now always carries an older revision than the stop's, and the upsert keeps the stop's row. The second test in `slide-run-stop.test.ts` replays it with the upsert unchanged, and `TurnStaysEnded` holds under `Saves` as it is. `19e91f75` had fenced a run that holds an element; `StopFencesHeldRun` checks that case.

Planted faults that the replay catches: stop_run of a run with no element not writing it ended, `runFenced` not reading the record, `liveTurn` taking a fenced run as the turn's run, and `readFresh` back to `base === deck.revision`. TLC fails `TurnCallsLand` with `Fresh == base = rev`.

One open turn per deck per agent holds by the table's primary key `(email, deck, agent)`. The model has one agent; a second agent's runs and turn are the agents model's. A person's protection lives in the deck's register, and every write to it is a compare-and-swap on `deck.saved.revision`, so a call on another server decides on the deck it read or does not land. edit and this replay cover that.

## slide-sibling

One live turn of run r. The agent read the deck at a base and sent two calls of the turn at once with that base: add_slide, and a second call (`second`): edit_deck of an element no person edits, or the same add_slide sent again with its once by a client that lost the first answer. A person may edit another element once, at any time. Each call reads the deck and decides, and `commitEdit` writes only if `deck.saved` still has the revision it read; a lost write tries again, up to three tries. The add's write and its once's row in `deck.once` are one statement, and `prepare` reads the once after the deck: a call whose once is spent answers what the landed send answered and writes nothing (`replayed`). The person's edit is `commitEdits`, one step. `last` and `since` are the deck's `lastRun`; `foreign` is the latest revision a write other than r's made.

- `TurnCallsBothLand`: calls of one live turn that touch different things both land, in any order of their reads and writes, when nothing but their run wrote after their base. Harm if broken: an agent that sends add_slide and an edit at once has one refused stale by its own sibling, which failed the `aira-stopped-landed` state of `tests/browser/design-states.spec.ts` at random.
- `EditLands`: the edit lands even when the person wrote, since it touches another element.
- `StaleOnlyForOthers`: a slide call is refused stale only when a write other than its run's landed after its base.
- `SlideOnOwnRead`: a slide lands only when nothing but its run wrote after its base, even when its run wrote last. Harm if broken: a person writes, the run writes, and a slide sent on the base before the person's write lands on a deck the agent never saw.
- `SentTwiceLandsOnce`: a call sent twice lands once, and the send that does not land answers what the other landed. Harm if broken: a client that lost an add_slide's answer and sent it again gets two slides.
- `AppliesOnce`, `WritesOnRead`: as in slide-run.

Bounds: two calls, one person edit, `Tries = 3`, the base's revision written by r or by another writer, the second call an edit or the add sent again. 169 states. Run: `pnpm check:specs slide-sibling`. Replay: `apps/api/src/slide-sibling.test.ts` drives every edge through the real `serveMcp` with `mcpSteps`, the person's edit through `commitEdits`, on Postgres, and compares `lastRun`, the once's row, each call's pause point, read revision, tries and answer; an answer whose revision is not past the revision its try read is `replayed`. The same file holds the race as four fixed tests, and four more for `edit_deck add shape` and `edit_deck delete`, which take the same `readFresh` and record the run through `landed`. `packages/engine/src/slide-base.test.ts` checks `readFresh` and `lastRun` for every slide tool and both element tools. Code: `readFresh` and `agentSlide` in `packages/engine/src/agent-slides.ts`, `deleteElement`, `addTextBox` and `ready` (the element tools' `readFresh` and `runFence`) in `packages/engine/src/agent-elements.ts`, `landed` and `wroteBy` in `packages/engine/src/call.ts`, `settledCall` in `packages/mcp/src/server.ts`, `prepare` and `commitEdit` in `apps/api/src/mcp.ts`, `commitEdits`, `readStoredOnce` and `writeRevision` in `apps/api/src/saved.ts`. `apps/api/src/agent-once.test.ts` holds the re-send as fixed tests: a second send after the first landed, and one that lands while the first waits at its deck write. Leaves out: how both calls join r (turn, `parallel-edits.test.ts`), the turn saves, the stop (slide-run), a person who edits the edit's own element (edit), the other three slide tools, which share `agentSlide`, and the two element tools, which share `readFresh`.

Planted faults: TLC fails `TurnCallsBothLand` with `Fresh == Base = rev`, `SlideOnOwnRead` with a `lastRun` that has no `since`, `SlideOnOwnRead` when a person's edit leaves `lastRun` standing, and `AppliesOnce` and `SentTwiceLandsOnce` when the once is never spent, as before the once: the second send lands a second slide in four steps. The replay fails on the first two in the code, and on a `prepare` that never reads the once or a `commitEdit` that never writes it.

Sync: `specs/slide-sibling/covers.json`.

## slide-undo

A person's run Undo of agent run r after r added a slide or deleted slide D, with the agent still calling, one request at a time, and a person who may delete D again once an Undo brought it back.

- `UndoAllOrNothing`: an Undo takes back every slide of r that shows, or none. Harm if broken: Undo leaves half of an agent's slide edit.
- `RefusedChangesNothing`: a refused Undo leaves the deck as it was.
- `UndoFences`: no slide of r lands once its Undo landed. Harm if broken: a slide the agent adds after Undo can never be undone with the run.
- `UndoReachesEverySlide`: a slide of r that shows and that no person moved can be taken back by run Undo.
- `RunUndoOnce`: a run's Undo lands at most once. After one landed, a later Undo of r is refused, even once a person put back what it took back. `undoableAt` refuses a slide row of r once a row of anyone but r removed or restored that slide since (`fencedSince`, as for elements), and the rows a run Undo writes carry no run. Harm if broken: a slide the agent deleted and the person deleted again after the first Undo comes back a second time.

run Undo of r writes r ended in the deck (`ended`), as stop_run does. The turn row still names r, but `liveTurn` no longer takes it as the turn's run, so the agent's next slide lands under a new run, which its own run Undo takes back (the last test in the replay file).

Bounds: r's first command adds a slide or deletes D (`dropped`), two agent slide calls, one stop, one person move, a person's delete of D after an Undo brought it back, two Undo tries. 146 states. Run: `pnpm check:specs slide-undo`. Replay: `apps/api/src/slide-undo.test.ts` drives every edge from both starts through `undoRun` in `apps/api/src/undo.ts`, `commitEdits` in `apps/api/src/saved.ts` for the person's move and delete, and whole `serveMcp` calls through `mcpSteps` in `apps/api/src/mcp-steps.ts`, on Postgres. Requests here run one after another, so PR 391's retry never fires: no write lands between a call's read and its write. Code: `undoSlides`, `undoableAt`, `fencedSince`, `undoOf` and `turnCommands` in `packages/document/src/person-undo.ts`, `undoRun` and `endSlides` in `packages/engine/src/call.ts`, `runFenced` in `packages/engine/src/agent-slides.ts`, `liveTurn` in `packages/mcp/src/turn.ts`. `undoableAt` reads where each slide of r sat before and after its command, and `undoOf` answers the commands that put it back, one for a slide, which `undoSlides` applies in order. Leaves out: interleaving inside a request (slide-run has it), a person's own undo of the move or of the delete, a person's delete and restore of a slide r added. After that, `fencedSince` refuses run Undo though the slide shows where r put it, as it does for an element, so in the code `UndoReachesEverySlide` holds for a slide that no person moved, removed or restored, and elements of r, among them a slide's background, a fill row on `<slide>.slide`. `undoSlides` turns back r's element adds and deletes in the same loop, which element models, and refuses the whole Undo when a person edited an element r added. Its group branch is structure's.

Fixed bug, from `30244817`: run Undo left the turn naming r, and `runFence` passed a run that holds no element, so the agent's next slide landed under the undone run, and every later run Undo of r was refused. Planted faults that the replay catches: run Undo not writing r ended, and `liveTurn` taking a fenced run as the turn's run.

Fixed bug: a second run Undo of r landed again for a slide command. r deleted D, its Undo brought D back, a person deleted D again, and a second Undo of r brought it back once more. `373e1cf5` fenced this for r's elements only. With `UndoApplies` as the code was, without `~fenced`, TLC fails `RunUndoOnce` in three steps: PersonUndoes, PersonDeletes, PersonUndoes. Without the slide fence in `undoableAt`, the replay fails, and so do its fixed test and `packages/engine/src/agent-slides.test.ts` ("refuses a second Undo of a run once a person deleted again the slide the first brought back").

Sync: `specs/slide-undo/covers.json`.
