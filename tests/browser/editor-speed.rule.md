# An open Doom deck that nobody touches works at most 150 ms in 3 s and runs no task over 50 ms of thread time, read over a quiet span the test does not drive

`tests/browser/editor-speed.spec.ts` traces the renderer over a kept 3 s wait and reads each top-level task on the page's renderer main thread by its thread time (`RunTask` `tdur`). The trace is the one interval for both checks: the tasks' thread time adds up to at most 150 ms, and no task runs over 50 ms. A task counts when the trace holds it whole, from after tracing starts until before it stops. A nested task counts once, inside the task that ran it. The test reads no clock to mark the window. The test sends no frame of its own in that span, so it reads only what the deck schedules: timers, animation frames, idle callbacks, observers, and the frames they cause.

The page's renderer main thread is the one the trace names for the page's own frame. `tracedSpans` in `tests/browser/renderer-thread.ts` asks the page's DevTools session for its main frame (`Page.getFrameTree`), finds that frame's renderer process in the trace's `TracingStartedInBrowser` event, and reads that process's `CrRendererMain` thread. A trace that names no process for the frame, or no main thread for that process, fails, so an empty trace is no reading. Until 2026-11-24 the checks read the busiest renderer main thread in the trace. A second tab spinning 35 ms every 80 ms read 1,263.9 ms in place of the editor's 14.0 ms, a site-isolated iframe doing the same read 1,263.5 ms in place of 12.6 ms, and typing beside either read no key at all. Read by the page's frame, the second tab's run read 12.8 ms while that tab's renderer worked 1,300 ms, the iframe's runs read 15.0 and 13.7 ms while its renderer worked 1,253 and 1,263 ms, and all 48 keys read in each.

A task holds an event that starts inside the task's wall span (`dur`), and thread time (`tdur`) is only the value read. Two tasks that start together are ordered outermost first. Chromium can report more thread time than wall time for one task: a 62.07 ms timer task read 62.97 ms of thread time, and key tasks read up to 9.77 ms of thread time over 8.49 ms of wall time. Until 2026-11-24 a task's span ran to the larger of the two, so a key that queued behind the timer started inside its span and read the timer's 62.97 ms in place of its own 3.5 ms.

Until 2026-11-24 the 50 ms check read a `longtask` entry's duration, which is wall time. The scheduler stopping the renderer for 105 ms inside one task read a 108 ms entry with 7.85 ms of thread work, so a busy machine failed a deck that did nothing. Read in thread time on the 40-slide deck, the same forced pause passed 7 of 7 runs, 2 quiet and 5 under 32 busy loops, while the `longtask` entry read 109 to 115 ms. A fixed loop that took 60 ms on its first runs failed 5 of 5 runs at 65.6 to 71.5 ms. A loop that spins until 60 ms of wall time pass failed 2 of 2 quiet runs (60.3 and 60.4 ms) and 4 of 5 loaded runs (54.3 to 60.4 ms). The fifth got about 49 ms of the core in its 60 ms, so the page did 49 ms of work, under the limit.

The 150 ms total budget alone misses a single slow periodic task. In the 2026-11-23 prototype, a planted 60 ms task every 2.5 s read 66.0, 67.5, and 69.0 ms total with fixed phase and 65.6 and 68.2 ms with random phase, passing the 150 ms total budget in all 5 runs even though a 60 ms task is a visible stutter. Adding the 50 ms long-task check failed that random-phase plant in 2 of 2 runs (74.3 ms total with a 61 ms task, and 67.7 ms total with a 56 ms task). On a clean 40-slide deck, the combined check read 10.5 and 10.6 ms alone, 9.3 to 10.5 ms across 3 parallel runs, and 12.1 and 17.0 ms under 6x CPU throttling, with 0 long tasks in every run. A planted 60 ms task every 1 s failed both checks at 177.9 ms total and 3 long tasks (longest 56 ms).

Shortening the wait, fake time, and virtual time were tried in the same prototype and rejected. A 1 s real wait with a 50 ms budget passed the random-phase 60 ms every 2.5 s plant in 4 of 6 runs (2.0 to 2.3 ms when the period missed the 1 s window, 58.1 and 63.3 ms when it hit) and passed the fixed-phase plant in 1 of 4 runs (47.9 ms). Playwright's `page.clock` fake time advanced 3000 ms in about 20 ms of wall time without driving frames, CSS animations, or observers, so it passed a `requestAnimationFrame` slide-move loop (15.2 ms, 2 layouts), a CSS width animation (5.3 and 5.4 ms, 1 layout, 17 ms animation advance), and a `ResizeObserver` loop (1.1 ms, 0 layouts). DevTools virtual time (`Emulation.setVirtualTimePolicy`) advanced 3000 ms in 14 to 23 ms of wall time and missed the same loops: `requestAnimationFrame` read 0.9 and 5.8 ms (0 to 1 layouts), the CSS width animation read 1.0 ms (0 layouts), the `ResizeObserver` loop read 0.9 and 1.0 ms (0 layouts), and even a 2 ms timer every 16 ms passed at 148.4 ms. Over a real 3 s quiet span, those same plants all failed: 420.5 and 422.4 ms for the 2 ms every 16 ms timer, 723.1 and 783.2 ms (180 layouts) for `requestAnimationFrame`, 737.7 and 770.2 ms (183 to 186 layouts) for the CSS animation, and 763.9 and 771.2 ms (180 layouts) for `ResizeObserver`.

Until 2026-11-23 the span was 180 animation frames the test requested itself. Each frame ran a full frame of the 40-slide editor, about 1 ms of style, intersection, and commit work, so the reading was mostly the test's own frames: 149 to 154 ms with three runs at once, and 524 to 618 ms under 6x CPU throttling.

An agent's edit paints in the open tab within a median of 80 ms of renderer thread time across five edits. The trace marks the parsed `since` reply carrying the edit's unique `once` and the resulting style mutation on the edited canvas node. It pairs the mutation with the first subsequent `Paint` in the page's renderer. Every top-level task from the arrival task through the paint task counts once, including tasks between the marks. The old `TaskDuration` delta included all renderer activity from the API post to the next frame.

A typed letter's work is the thread time of the renderer task that dispatched its keydown (`keyTasks` in `tests/browser/renderer-thread.ts`): the keydown, keypress and beforeinput handlers and the render of the edit they run. The test types 48 letters, and the first three are a named warmup (`warmupKeys` in `tests/browser/typed-letter.ts`). Two checks read the other 45. The mean of the fastest 43, leaving out the slowest 2 (`spikeKeys`), stays under 8 ms, which catches every letter getting slower. The mean of all 45 stays less than 1.2 ms beyond the typical letter, the median, which catches a share of letters getting slower while the typical letter does not.

Until 2026-11-24 a letter's reading was the renderer's `ScriptDuration` from the key press until two frames later. That window held whatever ran in it by the wall clock: the filmstrip thumbnail follows typing 150 ms later (`followMilliseconds` in `apps/web/src/editor/typing-preview.tsx`) with a render of about 4.6 ms, and it landed inside some letters' windows and outside others, along with the test's own frame wait. A busy machine stretches each window, so more of that work landed in it. Under 32 busy loops that reading went from 5.7 to 8.3 ms against the 8 ms limit, and 1 of 20 runs failed.

Normalizing by a fixed workload does not cancel the load. A fixed script workload timed in the same renderer after each letter read 3.8 to 4.4 ms on a quiet machine and 3.9 to 4.2 ms under 32 busy loops, while the letters' own tasks rose from a mean of 5.2 to 6.1 ms. The editor's work slows under contention for the core and its caches, and a small workload does not, so a ratio between them still moves with the load. Counting layouts, style recalculations or renders a letter does not see a slower handler that does the same layouts. A CPU profile of slow letters (8 to 14 ms) against fast ones (3 to 5 ms) found the same functions, `DoomCanvas`, `resolveSlide` and `solveLayout`, taking about twice as long. A slow letter ran no extra work.

Read this way, under 32 busy loops with one worker, 20 of 20 runs passed: the mean read 5.57 to 6.88 ms and the excess over the typical letter read -0.03 to 0.65 ms. On a quiet machine, 5 of 5 runs passed at 5.78 to 6.08 ms and 0.07 to 0.25 ms. After the page's own thread was read by its frame and a task's wall span decided which events it held, 20 of 20 loaded runs read 5.87 to 7.18 ms and 0.03 to 0.39 ms, and 5 of 5 quiet runs read 6.14 to 6.80 ms and -0.03 to 0.22 ms. `tests/typed-letter.test.ts` plants 10 and 20 ms on a fifth, two fifths, half, three fifths, four fifths and all of the letters, and passes a run where every letter is a fifth slower and a busy run where one lone letter stalls 40 ms beside letter 45.

On 2026-11-24 an unplanted quiet run failed the 8 ms mean at 8.13 ms, with a 7.24 ms median and a slowest letter of 22.8 ms. A probe that saved every task in the typing trace caught the same failure on its first run, at 10.55 ms. Letters 11 to 22 read 9 to 37 ms, where the run's other letters read 5 to 9 ms. Their extra time was the editor's own script, the `beforeinput` handler's call, running two to five times slower. No garbage collection, layout, style or font load ran inside them. Over the same 1.3 s, every other task on the renderer slowed alike. The test's own animation frames, which run no editor code, rose from about 1 ms to as much as 12.8 ms, and the frames that paint a letter rose from about 5 ms to 21 ms. Right after the run, other agents on the 48-CPU machine held 58 to 113 runnable tasks. When runnable tasks outnumber the cores, the kernel preempts the renderer mid-task and it resumes on cold caches, so the same work takes more thread time. Confining the browser to 8 CPUs reproduced it. With 0 or 8 busy loops on those CPUs, 6 of 6 runs passed at 4.66 to 6.72 ms. With 16 loops, two of three runs read a stretch of 9 to 11 letters in a row at two to four times their thread time, at 8.45 ms with 2.19 ms beyond typical and 7.14 ms with 2.10 ms beyond typical.

Thread time cannot tell that burst from a slowdown planted on a share of the letters, because both raise a share of the letters' own thread time. Dividing each letter by work beside it, such as the test's frames, would cancel the burst and also cancel a real slowdown that reaches the frames, so the checks do not divide. Dropping letters the kernel preempted does not help either: with 8 busy loops on 8 CPUs every letter was preempted, and those runs passed. What a statistic can drop is the lone spike. Across 10 quiet runs, the slowest two letters read 7.6 to 11.0 ms against medians of 6.1 to 6.9 ms. One of them is letter 45 in 9 of the 10 runs, which recalculates style for 1.3 to 1.9 ms where no other letter does. The other is a lone letter with no extra events. Leaving the slowest 2 of 45 out of the 8 ms mean moves a clean run's reading by 0.06 to 0.17 ms, and a slowdown on every letter moves the trimmed mean as much as the mean. The beyond-typical check still reads all 45, so a share of slow letters still counts in full. A failing speed guard reports `speed not measured` when a sample during its measured phase reaches the core count. The failure keeps the guard's numbers. Read this way, with one worker, 20 of 20 runs under 32 busy loops passed at 6.12 to 7.19 ms for the fastest 43 (6.23 to 7.38 ms for all 45) and −0.15 to 0.25 ms beyond typical. With the loops stopped, 10 of 10 passed at 6.18 to 7.45 ms (6.33 to 7.66 ms) and −0.09 to 0.23 ms. In the same runs the thumbnail render read 3.24 to 4.57 ms and its paint 2.88 to 4.83 ms over 12 to 17 updates, and no task while typing ran over 50 ms. Every plant in the table above failed again, each at the mean of the fastest 43, from 8.15 ms for 10 ms on 1 in 5 letters (1.92 ms beyond typical) to 24.93 ms for 20 ms on every letter.

Before measuring idle, typing, drag or the batch of five agent edits, the speed spec waits up to 120 seconds for `/proc/loadavg` to report fewer runnable tasks than available logical CPUs. The gate fails explicitly when that condition never holds. Only the time spent waiting for the machine is added to the spec’s execution deadline. It samples again every 100 ms during the measurement. On failure, `speed-tasks.json` contains the samples for each phase, the idle reading, the typed-letter, redraw and agent-paint tasks with their trace events, and long typing tasks. A passing guard stays successful even when load arrives after admission.

The speed spec and `verify-airdesign bench` take the same exclusive `~/.cache/airdesign/speed.lock`. The bench also keeps its slot in the regular check queue. The speed spec additionally takes `~/tmp/browser-4485.lock`, the coordinator's lock for browser runs. Run the speed spec with `pnpm test:browser --workers=1 editor-speed.spec.ts`. A coordinator command that already holds the browser lock passes that exclusion on to the spec. The CI browser shard that includes the speed spec uses one Playwright worker. Its GitHub-hosted `ubuntu-24.04` VM has four logical CPUs and runs one job.

Typing leaves the filmstrip's redraw for later. The first letter after a redraw starts a 150 ms timer (`followMilliseconds` in `apps/web/src/editor/typing-preview.tsx`), and the task that fires it renders the typed slide's thumbnail. The next animation frame's task paints it. Before typing, the test watches the typed slide's filmstrip entry with a `MutationObserver` that writes `console.timeStamp("typed-slide-thumbnail")` into the trace, so the mark lands inside the task that changed the thumbnail. A redraw (`thumbnailRedraws` in `tests/browser/renderer-thread.ts`) is a task that fires a timer a keydown's task installed and holds that mark, paired with the first later task that holds a `Paint`. A timer that changed no thumbnail is not a redraw, and the count of redraws is the count of thumbnail changes. The render tasks' mean thread time stays under 8 ms, and the paint tasks' mean stays under 8 ms, so each, beside a letter also under 8 ms, fits in one 16.7 ms frame. The test also checks that the thumbnail shows the typed letters and that at least 7 redraws were read. 48 letters two frames apart take at least 1.6 s, and a redraw follows every 150 ms plus at most one 33 ms letter gap, which gives about 8.7 redraws. One fewer allows for the last redraw, which may land after the trace ends.

Until 2026-11-24 nothing read the redraw. A 60 ms stall in its timer passed the whole spec. Under 32 busy loops, 20 of 20 runs read a 2.82 to 3.90 ms mean over 12 to 17 redraws. With the loops stopped, 5 of 5 runs read 2.72 to 3.53 ms over 12 to 14. Under load, each plant failed the check: 60 ms on every redraw read 62.16 ms, 10 ms on every redraw read 12.98 ms, and 30 ms on 1 in 3 read 13.26 ms. Until 2026-11-24 evening the check read the timer's task only and counted every timer a key installed. A 60 ms spin in the animation frame after each thumbnail change read 62.6 to 66.3 ms a task and passed, and with the real timer delayed to 4.5 s, unrelated zero-delay timers installed every third key read 16 redraws at 0.08 ms and passed. Read as above, the first plant read a 62.91 ms paint mean over 14 redraws and failed, and the second read 0 redraws and failed.

A letter can also leave work on a scheduler the letter and redraw checks do not read, such as a `MessageChannel` message or an animation frame. The typing trace holds the idle span's per-task limit: no task on the page's renderer runs over 50 ms of thread time while the letters are typed, whatever scheduled it. A planted 60 ms of work posted over a `MessageChannel` on every third letter read 16 tasks over 50 ms and failed. A 60 ms spin on the first letter alone, inside the warmup, read 1 task over 50 ms and failed. A smaller stall on another scheduler, such as 10 ms posted over a `MessageChannel` after each letter, stays under 50 ms, and no typing check reads it.

On 2026-11-24 a verifier run with a forced 105 ms pause in the idle span later failed typing at a 9.68 ms mean, 2.63 ms beyond typical, with no slowdown planted. That run held one renderer main thread, so it did not read another tab. Nine letters in a row read 11.5 to 32.7 ms. The renderer's thread time over the typing trace was 1,307 ms, against 743 to 1,125 ms in the other runs that day. The nine letters hold about 140 ms of that excess, so most of the extra work ran outside the letters' own tasks. The only way that work could reach a letter's reading was the overlap rule above: a letter that queued behind a task whose thread time ran past its wall end read that task's thread time. The run kept no per-task list, so it cannot show which letters read a neighbour. With the overlap rule removed, the same pause passed typing in 9 of 9 runs, quiet and under load, at 5.93 to 6.82 ms. Read both ways from those traces, the old and new rules gave every letter the same value. A second, unpinned stretch of extra renderer work would now show in no letter's reading, unless it ran inside the letters' own tasks.

Thread time sees main-thread work only. A heavy static CSS filter on the slide box read a drag frame of 10 ms against 20 and a delay of 33.2 ms against 50, and the task metric read 33.4 ms a frame. Paint that runs on the main thread shows in the task and script metrics. Compositor and GPU raster work shows in none of them, and the old gap between animation frames would have seen compositor lag. The task-per-frame limit stays, and a slowdown that lives only in the compositor or on the GPU is a thing these checks cannot catch.
