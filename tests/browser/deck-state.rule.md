# A failed browser test keeps the device's rows for each deck and the server's for each open deck, so a lost edit can be traced from what ci kept

The `deckState` fixture in `tests/browser/deck-test.ts` runs for every browser test, because every spec takes `test` from `deck-test.ts` or from `api-stack.ts`, which extends it, and `no-bare-test` fails a spec that takes `test` from `@playwright/test` (`tooling/oxlint-plugin-airdesign/rules/no-bare-test.rule.md`). A journey in `tests/journeys/journeys.spec.ts` adds the same `deckStateFixture` from `deck-state.ts`; it takes no `test` from `deck-test.ts`, because that file's imports of the app's copy break the journey kit's own import of it. Each time a page of the app loads, an init script reads the device's rows before the app's own code runs and hands them to the test, which keeps the last 4 loads in memory. A reload is one of those loads, so its entry holds what the reloaded page starts from: every row the old page stored before it went, and nothing the new page wrote. Reading after the old page goes, rather than before `page.reload()`, keeps the reload from waiting on a device write still in flight, which would hide the race a slow-device spec is built to catch.

When a test fails, the fixture writes `deck-state.json` beside its screenshot and attaches it under that name. It holds, per deck, the `confirmed` and `pending` rows, `head`, `revision`, `aside`, `sectionStarts` and the unsaved shelf from `localStorage`, the names of the other slots (a deck's parts and pictures are left out) and the kept loads. A passing test writes and attaches nothing, and so does a failed test that loaded no page of the app, such as one that drives only contexts it makes itself.

`tests/device-rows.test.ts` holds how keys group into decks. `scripts/land-report.test.mjs` and `scripts/race-issue.test.mjs` hold that a failed browser test's report and its `Race:` issue name `deck-state.json` (`scripts/deck-state-file.mjs`).

Measured on 2026-11-20 over 464 passing runs of the 116 tests in the 13 specs that reload most: setting the fixture up and tearing it down took 1.3 ms at the median, 8.4 ms at the 99th percentile and 15 ms at most, and no passing test attached anything. Over 75 reloads each, a reload took 633 ms to ready at the median without the fixture and 629 ms with it.

Measured on 2026-11-21 over 6 of the 92 specs that moved to the fixture (39 tests, 3 runs each way, 2 workers): leaving out the first test of each worker, the tests took 51.4 s before and 50.5 s after. The first test of a worker took up to 1.9 s longer, once per worker, because it now loads `packages/live/src/device.ts` for the fixture; a worker in a full run had loaded it already for the 139 specs that had the fixture.
