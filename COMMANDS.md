# Commands

What each command runs, its flags and its limits. `AGENTS.md` has the short loop; this file is the detail behind it.

- `pnpm gate` is what a push needs. It runs the cheap checks and the `sweep-list` step, builds the changed apps and packages and what depends on them, and runs the script tests `pnpm prove` picks: those that import a changed script and those that read a changed file by path, found by `scripts/script-test-reads.mjs`. The gate maps the diff with `scripts/change-map.mjs`, the map ci uses. It runs the changed unit test files in the map's folders, then the files Vitest relates to the change in those folders, cheapest first, until 15 estimated seconds: each file counts 1 s plus half the seconds Vitest recorded for it on this machine. When the map runs everything, it runs only the changed unit test files. Script tests run only when the map turns on `scripts`. Its last line, `CI will also run: …`, names the unit test files it left out and each part the map turned on. Each file runs in isolation, so the selected files can be judged independently. ci runs the full suite before merge. It skips the check line, runs tests niced on two workers and stamps a pass; `git push` refuses a commit with no stamp and names `pnpm land`. A failed `unit-tests` step stamps nothing; `pnpm land --check` stamps the commit only when every failed file passes alone, the branch changes none of them, and each race is recorded as an issue. Never `--no-verify`. `gate-duration` times it against a limit of 60 seconds.
- `ci` is the judge before the merge. On a PR, the `changes` job reads the PR's own diff, GitHub's merge commit against `HEAD^1`, with `scripts/change-map.mjs`, and runs only the parts that diff can affect: each check job, the corpus, journeys and design-findings run unless `changes` says their part is `false`, the source job runs only the unit test folders the map lists, and the model check runs only for a spec change. The metrics that read the whole unit run are then left to `main`. A docs-only PR runs `source` with no unit tests and `scripts`. A change to a `package.json`, the lockfile, `.github/`, the check runner, the map, shared test setup, or a path the map cannot place runs everything, and so does a diff that cannot be read. `ci` fails a skip that `changes` did not call for. The merge queue and pushes to `main` pass `--full`: the queue runs every step but the design scans and pptx, and main reuses the queue's run for the same commit. With no queue run for a commit, the push to `main` runs every part but the design scans itself, saves the caches a queue run used to hand it, and its time is `ci-duration`. The `file-growth` step blocks on a PR and only warns in the queue and on that push. `pptx` and `corpus` follow `.github/actions/ci-changes/pptx-paths.txt`. `node scripts/change-map.mjs --paths <file>` prints what a list of paths runs, one path per line. Mutation runs on every PR and blocks nothing. The browser shards and the two corpus shards split the spec files by their spec seconds in `tests/browser/spec-seconds.json`, the heaviest file to the lightest shard, so `pnpm check --part=browser --shard=<n>/<total>` runs the same files on your machine as on ci. A full run's unit tests split the same way into two source shards by the seconds in `tests/unit-seconds.json`, beside one source job that runs every other step once; a change that narrows the unit tests runs one source job with no shard (`scripts/unit-shards.rule.md`). A new spec with no record weighs the median. A local `pnpm test:browser` that passes whole files writes a new spec's seconds into that file, so commit it with the spec. On a PR the design scans run in one job per 200 states, each over its own share of the states and screens, and the `design-findings` job then judges the reports of every design job together; a missing report fails its step. A test the gate left out shows first there. `pnpm check` still runs the same steps on your machine when you want the full run, minus the browser tests, and a pass stamps the commit too. `pnpm check --all` keeps going and lists every failing step. Run the browser tests yourself with `pnpm test:browser`. The preview server starts at `AIRDESIGN_PORT`, or at 4400 plus a hash of the worktree path, moves up to the next free port when that one is taken, and reports the port it holds to Playwright, so two worktrees can run browser tests at once. A local browser run uses at most 4 workers, fewer on a small machine, and refuses a `--workers` above that unless the owner sets `AIRDESIGN_BROWSER_WORKERS`. One check runs per 16 cores and 12 GB of memory, at least one; `AIRDESIGN_CHECK_SLOTS` sets another count. A slot past the first opens only while the load average is below the core count. Once no slot is open, the next `pnpm check`, `check:pptx` or `suites --run` prints its place in line and waits. A job whose branch has older queue code than the newest on the machine fails at once and says to rebase onto `origin/main`. A test file that `pnpm land` reruns alone takes the small lane instead, which runs beside a full check, one job at a time, niced and on two workers. Benches, paint fidelity, `verify-airdesign` looks and before and after images, and `check:pptx` where it needs local tools run on this machine only when the diff needs them. A test that fails beside other work and passes alone has found a race: fix the race, never the test's wait.
- `pnpm land` lands changes on `main`. Run it in the branch's worktree after the last edit. It checks the base and title, rebuilds a branch that holds a merge commit as one commit on the `origin/main` it fetched (the merge queue rebases commit by commit and drops a merge commit as `merge_conflict`; the rebuild keeps the tree a merge gives, prints the head it replaced, and stops instead when the merge conflicts or files are uncommitted), tries the merge with `origin/main` and the migration numbers before the gate, runs `pnpm gate`, scans the commit for conflict markers, pushes with a lease, opens the PR against `main` when you give `--title` and `--body-file`, or sets an open PR's title, body and base from them, since `gh pr edit` fails on this repo, waits for ci to start on the head, and follows the required checks to merged. It judges green and failed only by the checks GitHub requires for `main`, read in the one pull request query: each check run's `isRequired` for that pull request, plus the contexts `refUpdateRule` lists for `main`, so a required check that has not started is waited for and never skipped. Today that is `ci` and `bar`. It merges as soon as those pass and fails the pull request as soon as one fails, without waiting for the rest of the run. Every other check, `mutation` and CodeQL included, is printed as `not required, blocks nothing: mutation still running` and decides nothing, and `mutation` keeps running and reports on the head after the merge. When GitHub names no required check, it merges nothing on that. Whether `main` has a merge queue it reads from GitHub on every look at the PR: a `mergeQueue` for `main` and an active ruleset with a `MERGE_QUEUE` rule on it. With a queue it queues the PR and reads the queue back. Right before it queues, or before it merges with no queue, it rechecks the head: it fetches `origin/main`, and when main has moved past the base the PR's ci tested, it merges main into the head as one commit in a scratch worktree under `~/tmp/recheck`, runs `pnpm gate --all` there, and stops with the failed steps and the main commits whose files the failure names. When `main` has no merge queue, it follows the required checks to green instead, rechecks the same way, reads `main` again, and merges only that head with `gh pr merge --rebase --match-head-commit`. When another PR merged during the recheck, or GitHub refuses the merge because `main` moved under it, it rechecks on the newer `main` and asks again, at most 3 rechecks; a moved head is refused and stops it, since the new head needs its own ci. It never arms auto-merge then, and switches off one armed earlier, so nothing merges without the recheck. `--watch` does the same. A recheck takes about a minute: the worktree and an offline install take 2 seconds, and the gate's own selection bounds the rest, which is the cheap rules, the build of the changed packages and what depends on them, and the unit test files that fit its 15-second budget. `node scripts/premerge-recheck.mjs <head>` runs one by hand. When only the `unit-tests` step failed, it runs each failed file alone once. A file that fails alone too is a fault and stops the push. A file that passes alone has a race. If the branch changes that file, the push stops and says to prove the race by forcing the gap: a delay that makes the old code fail every time, then the fix passing 5 times in a row with the same delay. If the branch does not change it, the push goes on only once the race is a GitHub issue titled `Race: <file> › <test>`, with the failure output and the commit; a later failure of the same test comments on that open issue. When the test's issue is closed by a merged pull request, a failure on a commit without that pull request's merge commit comments there that it predates the fix and files nothing, and a failure on a commit with it reopens that issue (`scripts/race-issue.rule.md`). Tests never retry. It never reruns ci: when a required check fails it prints the failed tests, the kept `test-results` artifact, and whether `main` moved or changed a failing test file, so you know when to rebase. When `ci` on main's latest push is red, the follow says so first. A failure that is main's own, in the same jobs and tests as main's red push runs and started while main was red, does not count against the PR. Land says `main is red since <commit>, not your change: <job>` and gives no advice to fix it. It waits for a push run on main to pass, naming an open revert of the first red commit, and then takes a run on that green main: it closes and reopens the PR, or queues it again, with a comment that says why. A failure that adds any test of its own is the PR's. When named browser, design or journeys tests fail and the pull request edits neither the failed test file nor any browser or journeys test, land takes one fresh run per head, whether or not the change map says the diff can affect the failed job. It comments once, saying the failure is in tests the pull request does not edit and that one fresh run will tell, closes and reopens the pull request, or requeues after a queue drop. Reopening selects every ci part so ci can run the failed jobs. Land files a race only after the fresh run on the same head passes the failed jobs, and names each issue. A fresh run that fails the same test again records nothing and stops for a fix, saying the test failed twice on this head so the change most likely causes it. A pull request that edits the failed test file takes no fresh run. Unknown flags stop it. `--status` prints where a PR stands, with the required checks and the others apart, and why the queue last dropped it, and changes nothing. `--watch` follows a PR to merged, through the queue or the recheck and merge, and exits 1 with the failed tests when ci fails or the queue drops it. `--check` stops after the gate's stamp. `--pr <number>` names a PR from any directory. Before the gate it also stops a branch that puts files back to content `main` has since replaced, which is what a squash or `git reset --soft` made from a stale tree does; a deliberate revert names each file in a `Reverts: <path>` line of the commit body.
- `pnpm check:pptx` is the extra step CI runs when a PR touches a path on `.github/actions/ci-changes/pptx-paths.txt`. It uses LibreOffice and poppler when the machine has both, or installs them into `~/.cache/pptx-tools` on first use. It needs the .NET 8 SDK.
- `pnpm check` prints the metrics, the numbers we want moved. Each has a goal or a limit in `metrics.json`. Pick one and move it. A PR does not write `known-failures` or `long-titles`: they are measured on each run.
- `pnpm sweep` lists the finished worktrees, branches, verify evidence and dead Postgres clusters on this machine, and `--apply` removes them. The `sweep-list` step lists the candidates in the gate, at most once every 30 minutes on a machine, because the list costs 20 seconds with many worktrees and is the same for every agent on the machine.
- `pnpm detach <script> [args]` starts `pnpm check`, `pnpm land`, `pnpm prove` or any script in its own session, writing its output to a log, so it keeps its place in the machine's line when the call that started it ends. `pnpm detach --wait` prints the new output and exits with the run's code when it ends, or with 75 after 8 minutes; run it again until it ends.
- `pnpm new:package <name>` creates a workspace package. Do not build one by hand.
- `pnpm rules [word]` prints every `.rule.md` as one table of rule, what holds it and its file, or only the rules that name the word. The `rule-rows` step of the gate and `ci` fails a new row of a `| Rule | Enforced by |` table that a check holds and names the `.rule.md` to write beside that check.
- `pnpm dev` inside `apps/web` or `apps/site` starts that app.
- `pnpm run deploy` inside `apps/site` or `apps/web` builds that app, stamps the commit on `/version`, and publishes it to Cloudflare. It does not deploy the API. After `ci` passes for a push to `main`, `.github/workflows/deploy.yml` deploys N, the newest commit on `main` whose push `ci` passed, to the site and the web app unless that app already serves N or a newer commit that contains it. A later run never puts an older commit live. Each app deploys on its own, so one red deploy does not stop the others, and a failed step files or updates that app's deploy-is-red issue. The same run moves branch `green` to N, fast-forward only, and creates it the first time. `green` is the deploy branch and must not be deleted. Railway builds the API from `green` without waiting for checks, because it skips a commit when any workflow on it fails, and runs the database setup before each deploy. `.railway/railway.ts` holds the settings. Variables stay on Railway. After that file merges, apply it with `railway config apply`. Until that apply, Railway still follows `main`. A hand `pnpm run deploy` is for emergencies. The production journey then waits until the web app and the API both serve N, or a newer commit that contains it, and tests that commit.
- When `ci` fails on a push to `main`, the red-main bot checks which jobs the change map says the diff can affect. It records a test as a race at once if the map rules out every job that failed it. A failed check step such as typecheck or a failed browser test whose file changed is a certain red. The bot opens a revert and merges it if its ci passes while main is red. A failed unit or script test gets a green rerun with the same seed and path. If it fails the same way there, the bot files an `Old fault:` issue. For a suspect browser failure, the revert waits for a second failure of the same test and a passing green rerun. If a green push comes first, the bot records the race even when the revert conflicted or a later push is already red. A failed revert gets one fresh run if the map rules out its failed jobs. The bot records those races and reopens the revert as the owner. If the fresh run fails, or the revert can affect a failed job, the bot reports the stop on the `main is red` issue. To drill a verdict without opening a revert, run `gh workflow run red-main-revert.yml --ref <branch> -f rerun_run=<run id>`. See `scripts/red-main-revert.rule.md`.

`scripts/check-steps.mjs` declares each step once. A row with a name, kind, and command runs in the first stage of the `source` part, on this machine and on ci. Set `preflight` to run before the machine line and `gate` to join the gate. Steps with the same `lane` run in table order. Set `after: "work"` to wait for the first stage to finish. Rule, test, and build failures block by default. Reports make no judgment, and a report command that fails still fails the run.

The `scripts` part runs the `script-tests` step through `pnpm test:tooling`, the `site-build` step, and the `test-imports` step. The browser and design parts run the `browser-build` step before the `browser-tests` step. A standalone `pnpm test:browser` runs the same build before starting Playwright. The `findings` part runs the `test-imports` and `design-findings` steps on the design reports the design jobs wrote.

In ci, check streams step output and names each step as it starts. The step limit is 20 minutes, with 15 minutes for browser tests and 8 minutes for design findings. Playwright also limits the browser test run itself to 10 minutes.

`main` only accepts commits whose PR passed the `ci` and `bar` checks, so every change goes through a PR against `main`, never against another PR's branch. `pnpm land` rechecks the head on the newest `main` and merges it with a rebase, which keeps commit authorship; the push to `main` then runs all of `ci`, and the revert bot undoes a red one. While the ruleset "merge queue on main" is active, the PR enters the queue once its checks pass instead, and the queue tests it on top of the latest `main`, together with the PRs ahead of it. `.github/branch-protection.rule.md` has the guarantee and the rollback. Do not rebase a PR only because `main` moved. Rebase only when GitHub reports a conflict. The `bar` check is required. It fails on a PR body that `pnpm land` would refuse (`scripts/pr-body.mjs`), and in the merge queue, when there is one, it passes at once. It lists what the PR lowers: a raised limit, a moved goal, a metric moved away from its goal, a removed metric, check step, workflow job, spec invariant, case, deck or caught break, a new skipped test, a check step made a warning or local only, or a lint or type rule turned down. It labels that PR `lowers-the-bar`. It labels `changes-ci` a PR that changes which checks run or how they judge: workflows, check steps and check scripts, test selection, the gate, and lint and type config. A PR that only adds or changes tests, cases, fixtures, specs, land and report tools, or docs gets neither label. `scripts/bar-files.mjs` names each kind of file. The owner reads both labels after the merge. A `lowers-the-bar` PR also fails `bar` until it has a countersign for its current head: a comment `countersign <head> right: <one-line reason>` from an agent that did not write it, posted with `node scripts/countersign.mjs <pr> <head> right "<reason>"`. That agent gets only the PR number, reads the bar's list with `node scripts/countersign.mjs <pr>` and the diff, and never the PR's body or comments. The comment starts `bar` again through `.github/workflows/countersign.yml`; a new push makes it stale. `pnpm land` arms auto-merge when `main` has a queue, prints the verifier's brief and stops; once `bar` passes, `pnpm land --watch` takes it to merged. `pnpm check` prints the same list locally, as its `bar` step, against where the branch left `origin/main`. Undo unintended changes on that list.
