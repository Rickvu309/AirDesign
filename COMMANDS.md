# Commands

What each command runs, its flags and its limits. `AGENTS.md` has the short loop; this file is the detail behind it.

- `pnpm gate` is what a push needs. It runs the cheap checks (format, lint, file size, references, bug rule, commit authors, boundaries, actionlint, product-copy literals), sweeps merged worktrees, builds the changed apps and packages and what depends on them, and runs the unit and tooling tests `pnpm prove` picks for the diff: every unit test file the diff reaches while there are 40 or fewer, past that only the changed test files. It skips the check line, runs tests niced on two workers and stamps a pass; `git push` refuses a commit with no stamp and names `pnpm land`. A failed `test` stamps nothing; `pnpm land --check` stamps the commit once every failed file passes alone. Never `--no-verify`. `gate-duration` times it against a limit of 60 seconds.
- `ci` runs every step of `pnpm check` on every PR, and all but the design scans and pptx in the merge queue, and it is the judge before the merge: the full unit suite, TLA+ specs, metrics, the browser shards, journeys, corpus and mutation. A test the gate left out shows first there. `pnpm check` still runs the same steps on your machine when you want the full run, minus the browser tests, and a pass stamps the commit too. `pnpm check --all` keeps going and lists every failing step. Run the browser tests yourself with `pnpm test:browser`. A local browser run uses at most 4 workers, fewer on a small machine, and refuses a `--workers` above that unless the owner sets `AIRDESIGN_BROWSER_WORKERS`. One check runs per 16 cores and 12 GB of memory, at least one; `AIRDESIGN_CHECK_SLOTS` sets another count. A slot past the first opens only while the load average is below the core count. Once no slot is open, the next `pnpm check`, `check:pptx` or `suites --run` prints its place in line and waits. A job whose branch has older queue code than the newest on the machine fails at once and says to rebase onto `origin/main`. A test file that `pnpm land` reruns alone takes the small lane instead, which runs beside a full check, one job at a time, niced and on two workers. Benches, paint fidelity, `verify-airdesign` looks and before and after images, and `check:pptx` where it needs local tools run on this machine only when the diff needs them. A test that fails only under load is not a reason to change the test.
- `pnpm land` lands changes on `main`. Run it in the branch's worktree after the last edit. It checks the base and title, tries the merge with `origin/main` and the migration numbers before the gate, runs `pnpm gate`, scans the commit for conflict markers, pushes with a lease, opens the PR against `main` when you give `--title` and `--body-file`, or sets an open PR's title, body and base from them, since `gh pr edit` fails on this repo, waits for ci to start on the head, queues it, reads the merge queue back, and follows ci to merged. When only `test` failed, it runs each failed file alone once and proceeds only if all pass, distinguishing machine load from a fault. Tests never retry. It never reruns ci on the same snapshot: when ci fails it prints the failed tests, the kept `test-results` artifact, and whether `main` moved or changed a failing test file, so you know when to rebase. Unknown flags stop it. `--status` prints where a PR stands and why the queue last dropped it, and changes nothing. `--watch` follows a queued PR and exits 1 with the failed tests when ci fails or the queue drops it. `--check` stops after the gate's stamp. `--pr <number>` names a PR from any directory. Before the gate it also stops a branch that puts files back to content `main` has since replaced, which is what a squash or `git reset --soft` made from a stale tree does; a deliberate revert names each file in a `Reverts: <path>` line of the commit body.
- `pnpm check:pptx` is the extra step CI runs when a PR touches `packages/pptx` or the PowerPoint check. It uses LibreOffice and poppler when the machine has both, or installs them into `~/.cache/pptx-tools` on first use. It needs the .NET 8 SDK.
- `pnpm check` prints the metrics, the numbers we want moved. Each has a goal or a limit in `metrics.json`. Pick one and move it. A PR does not write `known-failures` or `long-titles`: they are measured on each run.
- `pnpm sweep` lists the finished worktrees, branches, verify evidence and dead Postgres clusters on this machine, and `--apply` removes them. Every `pnpm check` lists the candidates.
- `pnpm detach <script> [args]` starts `pnpm check`, `pnpm land`, `pnpm prove` or any script in its own session, writing its output to a log, so it keeps its place in the machine's line when the call that started it ends. `pnpm detach --wait` prints the new output and exits with the run's code when it ends, or with 75 after 8 minutes; run it again until it ends.
- `pnpm new:package <name>` creates a workspace package. Do not build one by hand.
- `pnpm dev` inside `apps/web` or `apps/site` starts that app.
- `pnpm run deploy` inside `apps/site` or `apps/web` builds that app and publishes it to Cloudflare with `wrangler deploy`. It does not deploy the API. A commit on `main` that passed `ci` deploys both the same way when it is still the tip of `main`, in `.github/workflows/deploy.yml`. Each app deploys on its own, so one red deploy does not stop the other. So `pnpm run deploy` by hand is for emergencies. Railway builds the API from GitHub `main` and deploys every commit without waiting for checks, because it skips a commit when any workflow on it fails, and runs the database setup before each deploy. `.railway/railway.ts` holds the Railway project's settings. Variables stay on Railway. After a change to that file merges, apply it with `railway config apply`.

`main` only accepts commits that passed the `ci` check, so every change goes through a PR against `main`, never against another PR's branch. The PR enters the queue once its checks pass. The queue tests it on top of the latest `main`, together with the PRs ahead of it, and merges it with a rebase, which keeps commit authorship. Do not rebase a PR only because `main` moved. Rebase only when GitHub reports a conflict. The `bar` check never stops a merge, but it fails on a PR body that `pnpm land` would refuse (`scripts/pr-body.mjs`). It lists what the PR lowers: a raised limit, a moved goal, a removed metric, a metric moved away from its goal, or a changed PowerPoint case or deck the check already judges. It labels that PR `lowers-the-bar`, and it labels a PR that changes what `ci` checks `changes-ci`. The owner reads both labels after the merge. `pnpm check` prints the same list locally, as its `bar` step, against where the branch left `origin/main`. Undo unintended changes on that list.
