# Commands

What each command runs, its flags and its limits. `AGENTS.md` has the short loop; this file is the detail behind it.

- `pnpm gate` is what a push needs. It runs the cheap checks and the `sweep-list` step, builds the changed apps and packages and what depends on them, and runs the script tests `pnpm prove` picks. The gate runs every unit test file the diff reaches up to 40 files. Above 40 or when `pnpm prove --plan` calls for the full unit suite, the gate runs only changed unit test files and names what it leaves to ci. Each file runs in isolation, so the selected files can be judged independently. ci runs the full suite before merge. It skips the check line, runs tests niced on two workers and stamps a pass; `git push` refuses a commit with no stamp and names `pnpm land`. A failed `unit-tests` step stamps nothing; `pnpm land --check` stamps the commit once every failed file passes alone. Never `--no-verify`. `gate-duration` times it against a limit of 60 seconds.
- `ci` runs every step of `pnpm check` on every PR, and all but the design scans and pptx in the merge queue, and it is the judge before the merge: the full unit suite, TLA+ specs, metrics, the browser shards, journeys, corpus and mutation. On a PR the design scans run in one job per 200 states, each over its own share of the states and screens, and the `design-findings` job then judges the reports of every design job together; a missing report fails its step. A test the gate left out shows first there. `pnpm check` still runs the same steps on your machine when you want the full run, minus the browser tests, and a pass stamps the commit too. `pnpm check --all` keeps going and lists every failing step. Run the browser tests yourself with `pnpm test:browser`. A local browser run uses at most 4 workers, fewer on a small machine, and refuses a `--workers` above that unless the owner sets `AIRDESIGN_BROWSER_WORKERS`. One check runs per 16 cores and 12 GB of memory, at least one; `AIRDESIGN_CHECK_SLOTS` sets another count. A slot past the first opens only while the load average is below the core count. Once no slot is open, the next `pnpm check`, `check:pptx` or `suites --run` prints its place in line and waits. A job whose branch has older queue code than the newest on the machine fails at once and says to rebase onto `origin/main`. A test file that `pnpm land` reruns alone takes the small lane instead, which runs beside a full check, one job at a time, niced and on two workers. Benches, paint fidelity, `verify-airdesign` looks and before and after images, and `check:pptx` where it needs local tools run on this machine only when the diff needs them. A test that fails only under load is not a reason to change the test.
- `pnpm land` lands changes on `main`. Run it in the branch's worktree after the last edit. It checks the base and title, rebuilds a branch that holds a merge commit as one commit on the `origin/main` it fetched (the merge queue rebases commit by commit and drops a merge commit as `merge_conflict`; the rebuild keeps the tree a merge gives, prints the head it replaced, and stops instead when the merge conflicts or files are uncommitted), tries the merge with `origin/main` and the migration numbers before the gate, runs `pnpm gate`, scans the commit for conflict markers, pushes with a lease, opens the PR against `main` when you give `--title` and `--body-file`, or sets an open PR's title, body and base from them, since `gh pr edit` fails on this repo, waits for ci to start on the head, queues it, reads the merge queue back, and follows ci to merged. When only the `unit-tests` step failed, it runs each failed file alone once and proceeds only if all pass, distinguishing machine load from a fault. Tests never retry. It never reruns ci: when ci fails it waits for the whole run, prints the failed tests, the kept `test-results` artifact, and whether `main` moved or changed a failing test file, so you know when to rebase. When only browser or journeys tests outside the diff failed, unchanged by it and with nothing under `tests/browser/` touched, it takes one fresh run per head: it comments on the PR why, then closes and reopens it, or queues it again after a queue drop, and re-arms auto-merge. The reopen keeps the branch because the `closed-branch` workflow waits 60 seconds and deletes only the branch of a pull request that is still closed; GitHub cannot reopen a pull request whose branch is gone. That comment is the record, so a second failure on the same head stops. Unknown flags stop it. `--status` prints where a PR stands and why the queue last dropped it, and changes nothing. `--watch` follows a queued PR and exits 1 with the failed tests when ci fails or the queue drops it. `--check` stops after the gate's stamp. `--pr <number>` names a PR from any directory. Before the gate it also stops a branch that puts files back to content `main` has since replaced, which is what a squash or `git reset --soft` made from a stale tree does; a deliberate revert names each file in a `Reverts: <path>` line of the commit body.
- `pnpm check:pptx` is the extra step CI runs when a PR touches `packages/pptx` or the PowerPoint check. It uses LibreOffice and poppler when the machine has both, or installs them into `~/.cache/pptx-tools` on first use. It needs the .NET 8 SDK.
- `pnpm check` prints the metrics, the numbers we want moved. Each has a goal or a limit in `metrics.json`. Pick one and move it. A PR does not write `known-failures` or `long-titles`: they are measured on each run.
- `pnpm sweep` lists the finished worktrees, branches, verify evidence and dead Postgres clusters on this machine, and `--apply` removes them. The `sweep-list` step lists the candidates.
- `pnpm detach <script> [args]` starts `pnpm check`, `pnpm land`, `pnpm prove` or any script in its own session, writing its output to a log, so it keeps its place in the machine's line when the call that started it ends. `pnpm detach --wait` prints the new output and exits with the run's code when it ends, or with 75 after 8 minutes; run it again until it ends.
- `pnpm new:package <name>` creates a workspace package. Do not build one by hand.
- `pnpm rules [word]` prints every `.rule.md` as one table of rule, what holds it and its file, or only the rules that name the word. The `rule-rows` step of the gate and `ci` fails a new row of a `| Rule | Enforced by |` table that a check holds and names the `.rule.md` to write beside that check.
- `pnpm dev` inside `apps/web` or `apps/site` starts that app.
- `pnpm run deploy` inside `apps/site` or `apps/web` builds that app and publishes it to Cloudflare with `wrangler deploy`. It does not deploy the API. A commit on `main` that passed `ci` deploys both the same way when it is still the tip of `main`, in `.github/workflows/deploy.yml`. Each app deploys on its own, so one red deploy does not stop the other. So `pnpm run deploy` by hand is for emergencies. Railway builds the API from GitHub `main` and deploys every commit without waiting for checks, because it skips a commit when any workflow on it fails, and runs the database setup before each deploy. `.railway/railway.ts` holds the Railway project's settings. Variables stay on Railway. After a change to that file merges, apply it with `railway config apply`.

`scripts/check-steps.mjs` declares each step once. A row with a name, kind, and command runs in the first stage of the `source` part, on this machine and on ci. Set `preflight` to run before the machine line and `gate` to join the gate. Steps with the same `lane` run in table order. Set `after: "work"` to wait for the first stage to finish. Rule, test, and build failures block by default. Reports make no judgment, and a report command that fails still fails the run.

The `scripts` part runs the `script-tests` step through `pnpm test:tooling`, the `site-build` step, and the `test-imports` step. The `browser-tests` step runs `pnpm test:browser`. The `findings` part runs the `test-imports` and `design-findings` steps on the design reports the design jobs wrote.

`main` only accepts commits that passed the `ci` check, so every change goes through a PR against `main`, never against another PR's branch. The PR enters the queue once its checks pass. The queue tests it on top of the latest `main`, together with the PRs ahead of it, and merges it with a rebase, which keeps commit authorship. Do not rebase a PR only because `main` moved. Rebase only when GitHub reports a conflict. The `bar` check is required. It fails on a PR body that `pnpm land` would refuse (`scripts/pr-body.mjs`), and in the merge queue it passes at once. It lists what the PR lowers: a raised limit, a moved goal, a metric moved away from its goal, a removed metric, check step, workflow job, spec invariant, case, deck or caught break, a new skipped test, a check step made a warning or local only, or a lint or type rule turned down. It labels that PR `lowers-the-bar`. It labels `changes-ci` a PR that changes which checks run or how they judge: workflows, check steps and check scripts, test selection, the gate, and lint and type config. A PR that only adds or changes tests, cases, fixtures, specs, land and report tools, or docs gets neither label. `scripts/bar-files.mjs` names each kind of file. The owner reads both labels after the merge. A `lowers-the-bar` PR also fails `bar` until it has a countersign for its current head: a comment `countersign <head> right: <one-line reason>` from an agent that did not write it, posted with `node scripts/countersign.mjs <pr> <head> right "<reason>"`. That agent gets only the PR number, reads the bar's list with `node scripts/countersign.mjs <pr>` and the diff, and never the PR's body or comments. The comment starts `bar` again through `.github/workflows/countersign.yml`; a new push makes it stale. `pnpm land` arms auto-merge, prints the verifier's brief and stops. `pnpm check` prints the same list locally, as its `bar` step, against where the branch left `origin/main`. Undo unintended changes on that list.
